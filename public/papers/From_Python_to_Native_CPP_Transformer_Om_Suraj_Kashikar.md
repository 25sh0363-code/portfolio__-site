## Abstract

This study presents a controlled empirical performance comparison between Python/PyTorch and native C++/LibTorch implementations of a small decoder-only Transformer trained on the TinyStories V2 dataset. Both implementations consume identical pre-tokenized uint16 binary shards produced via the GPT-2 tiktoken tokenizer, enforce a 256-token context length, and implement matched 8-block Pre-LayerNorm Transformer architectures. Training and autoregressive inference were benchmarked on a dedicated NVIDIA GeForce RTX 4090 GPU. The native C++ implementation achieved a sustained training throughput of ~97,500 tokens/sec compared to ~60,000 tokens/sec in Python (a 1.63× advantage / +62.5% speedup), despite Python using CUDA Automatic Mixed Precision (AMP) with GradScaler while C++ executed in full FP32. In autoregressive inference, C++ delivered a median throughput of 190.6 tokens/sec versus 129.0 tokens/sec in Python (+47.8% speedup). Furthermore, C++ reduced inference GPU VRAM allocation by 69.8% (164.8 MB vs. 545.0 MB) and system host RAM by 18.0% (864.7 MB vs. 1,055 MB). Both implementations demonstrated equivalent validation loss trajectories, converging to ~1.41 held-out cross-entropy loss over 100,000 steps (819.2 million tokens).

**Research Question:**  
*How do Python/PyTorch and C++/LibTorch implementations of the same small decoder-only Transformer compare in training throughput, autoregressive inference throughput, and recorded memory use on an NVIDIA RTX 4090?*

## 1. Introduction

Modern deep learning research and deployment rely heavily on high-level Python interfaces such as PyTorch. While PyTorch delegates compute-intensive linear algebra kernels to highly optimized backend libraries (CUDA, cuBLAS, cuDNN), Python itself remains an interpreted language with dynamic typing, reference-counting garbage collection, and the Global Interpreter Lock (GIL). 

For high-throughput systems, low-latency edge applications, and resource-constrained environments, host-side overhead—including interpreter dispatch latency, object allocation, and serialization across language boundaries—can introduce tangible bottlenecks. LibTorch, PyTorch's underlying C++ API, provides native access to the ATen tensor library and PyTorch neural network modules without Python runtime dependencies.

This study systematically measures the empirical performance delta between Python/PyTorch and compiled native C++/LibTorch for an end-to-end decoder-only Transformer pipeline, evaluating both sustained training throughput across 100,000 gradient updates and autoregressive token generation.

## 2. Dataset and Preprocessing Pipeline

To eliminate confounding variables stemming from data loading, tokenization discrepancies, or differing data orders, both implementations share an identical preprocessing workflow:

1. **Corpus:** The TinyStories V2 dataset (Eldan & Li, 2023), consisting of synthetic narratives generated by GPT-3.5 and GPT-4 designed to teach language models coherent English syntax, grammar, and reasoning at compact parameter scales.
2. **Tokenization:** Text was tokenized in Python using OpenAI's `tiktoken` library with the standard GPT-2 byte-pair encoding (vocab size: 50,257).
3. **Binary Packaging:** Token streams were pre-tokenized and serialized directly into flat, memory-mappable raw binary files (`train.bin` and `val.bin`) containing continuous 16-bit unsigned integers (`uint16`).
4. **Zero-Drift Consumption:** Both the Python training script and the C++ executable stream directly from these identical binary shards. No online tokenization or text parsing occurs during training or evaluation.

## 3. Transformer Architecture & Mathematical Formulation

The model is an autoregressive decoder-only Transformer conforming to the Pre-LayerNorm GPT architecture:

### 3.1 Architectural Hyperparameters
- **Vocabulary Size ($V$):** 50,257
- **Context Length ($T$):** 256 tokens
- **Transformer Blocks ($N$):** 8 layers
- **Attention Heads ($H$):** 8 heads
- **Embedding Dimension ($d_{model}$):** 384
- **Head Dimension ($d_k$):** $384 / 8 = 48$
- **MLP Hidden Width ($d_{ff}$):** 1,536 ($4 \times d_{model}$)
- **Positional Encoding:** Learned positional embedding matrix $W_{pos} \in \mathbb{R}^{T \times d_{model}}$
- **Weight Tying:** The output projection layer shares weight tensors with the input token embedding table.
- **Dropout:** $p = 0.1$ applied to attention weights, MLP projections, and residual connections.

### 3.2 Attention Formulation
Each attention head computes scaled dot-product attention with a strictly enforced lower-triangular causal mask $M \in \mathbb{R}^{T \times T}$:

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{Q K^T}{\sqrt{d_k}} + M\right) V$$

where $M_{i,j} = -\infty$ for $j > i$ and $0$ for $j \le i$.

### 3.3 Feed-Forward Network
Each block contains a position-wise two-layer feed-forward network with Gaussian Error Linear Unit (GELU) activation:

$$\text{FFN}(x) = \text{GELU}(x W_1 + b_1) W_2 + b_2$$

where $W_1 \in \mathbb{R}^{d_{model} \times d_{ff}}$ and $W_2 \in \mathbb{R}^{d_{ff} \times d_{model}}$.

## 5. Training Methodology & Empirical Results

### 5.1 Training Configuration
- **Optimizer:** AdamW ($\beta_1 = 0.9, \beta_2 = 0.95, \epsilon = 10^{-8}$, weight decay = $0.1$)
- **Batch Size:** 32 sequences $\times$ 256 tokens = 8,192 tokens per parameter update
- **Total Steps:** 100,000 steps ($819.2 \times 10^6$ total tokens processed)
- **Learning Rate Schedule:** Cosine annealing with linear warmup
  - Peak learning rate: $5.0 \times 10^{-4}$
  - Minimum learning rate: $5.0 \times 10^{-5}$
  - Warmup duration: 2,000 steps
- **Precision Mode:** Python utilized CUDA Automatic Mixed Precision (`torch.cuda.amp.autocast`) with `GradScaler`. C++ LibTorch was executed in full single precision (FP32).

### 5.2 Training Throughput Comparison
- **Python (PyTorch + AMP):** 59,000 to 62,000 tokens/sec (midpoint ~60,000 tokens/sec)
- **C++ (LibTorch FP32):** 95,000 to 100,000 tokens/sec (midpoint ~97,500 tokens/sec)
- **Throughput Advantage:** **1.63× speedup (+62.5%)** for native C++. Across boundary ranges, the relative advantage spans 1.56× to 1.69×.

## 6. Inference Benchmarking & Memory Profiling

Autoregressive inference was evaluated using the shared prompt:  
`"A small dog found a shiny ball"`  
Parameters: maximum generation length = 256 tokens, temperature = 0.8, top-$k$ = 50, stopping on `<|endoftext|>`.

### 6.1 Inference Speed (Tokens per Second)
- **C++ (LibTorch):** Run 1 = 190.6 tok/s (0.666s), Run 2 = 190.6 tok/s (0.666s), Run 3 = 192.25 tok/s (0.659s).  
  **Median: 190.6 tokens/sec**
- **Python (PyTorch):** Run 1 = 129.0 tok/s (0.61s), Run 2 = 123.0 tok/s (0.62s), Run 3 = 130.0 tok/s (0.61s).  
  **Median: 129.0 tokens/sec**
- **Speedup:** **+47.8% (1.48× advantage)** for native C++.

### 6.2 Memory Allocation Footprint
- **GPU VRAM During Inference:**
  - Python: 545.0 MB
  - C++ LibTorch: 164.78 MB

- **Host System RAM During Inference:**
  - Python: 1,055.0 MB
  - C++ LibTorch: 864.7 MB
  - **Reduction: 18.0% lower RAM** in C++

## 7. Systems & Engineering Analysis

1. **Kernel Launch and Dispatch Overhead:** PyTorch relies on CPython's foreign function interface (FFI) and dispatch mechanism to issue CUDA kernels. For compact models where individual kernel execution time is on the order of microseconds, Python dispatch latency constitutes a substantial fraction of total wall-clock time. In native C++, kernel launches occur with minimal host CPU serialization.
2. **Autoregressive Loop Serialization:** Autoregressive decoding is inherently sequential—each token requires a forward pass through the entire network. Python repeats interpreter dispatch for every single generated token, compounding overhead over hundreds of sequential iterations. C++ eliminates this overhead entirely.
3. **Memory Allocator Overhead:** Python process memory includes the CPython runtime, loaded dynamic libraries, and Python object wrappers for tensors. In contrast, native C++ executes with minimal runtime scaffolding, resulting in substantially reduced host memory footprints.

---

## 8. Threats to Validity & Limitations

1. **Framework vs. Kernel-Level Implementation:** The comparison is between Python/PyTorch and C++/LibTorch rather than custom hand-written CUDA kernels. LibTorch still invokes the underlying ATen library kernels.
2. **Precision Discrepancy in Training:** Python was trained using CUDA AMP (FP16 math on tensor cores with FP32 master weights and GradScaler), while C++ was executed in FP32. C++ outperforming Python despite computing in FP32 indicates that the host dispatch bottleneck in Python outweighed the compute speedup of mixed-precision tensor cores at this model scale.
3. **Random Initialization:** Models were initialized with independent random seeds; while convergence trajectories match closely, individual parameter weights differ.
4. **Stochastic Generation Length:** Due to random sampling and EOT token emission, exact token lengths varied between runs (80 tokens in Python vs. 126 tokens in C++).

---

## 9. Conclusion

This study demonstrates that migrating a decoder-only Transformer pipeline from Python/PyTorch to compiled native C++/LibTorch yields significant improvements in both training throughput (+62.5% / 1.63×) and autoregressive inference speed (+47.8% / 1.48×), alongside dramatic reductions in GPU VRAM (-69.8%) and host RAM (-18.0%) on an NVIDIA RTX 4090. These findings illustrate the magnitude of Python interpreter dispatch overhead in small-to-medium Transformer workloads and highlight native C++ execution as a compelling paradigm for latency-critical and memory-constrained deployments.
